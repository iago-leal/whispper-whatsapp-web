1. Defeito

Transcrever de novo um áudio já transcrito falha: o motor recebe o áudio vazio. Depois de recarregar a página (Command R) ou numa aba nova, o clique no ícone de um áudio que a extensão já obteve uma vez termina em FALHA_NA_TRANSCRICAO, "Falhou após 0 s". Áudios nunca obtidos funcionam, o que fazia a falha parecer intermitente.

Escopo decidido por iago (19:55): o clique volta a produzir texto depois de recarregar. O texto anterior não reaparece sozinho: o cache de texto vive na memória da aba (RF-06), e guardá-lo entre recargas é feature à parte, que conflita com o RF-14 do núcleo.

2. Causa raiz confirmed

A ponte da extensão, no mundo da página, transfere ao script de conteúdo o próprio ArrayBuffer que downloadAndMaybeDecrypt devolve. O WhatsApp Web grava esse mesmo objeto no seu cache persistente de mídia depois de pelo menos um await; a transferência o desanexa antes, e o cache guarda 0 bytes, para sempre.

  1. pagina/ponte-audio.ts, atender: porta.postMessage({ ...audio }, [audio.bytes]), linha nascida em c76605f (CHG-001 do 2MOY).
  2. WhatsApp, WAWebMediaStoreLruImpl.doPut: enfileira a gravação, grava os metadados no IndexedDB e só então WAWebKeyValueCacheStore faz cache.put(chave, new Response(buffer)), no Cache Storage lru-media-array-buffer-cache, com o buffer já vazio.
  3. WhatsApp, doGet: devolve o buffer do cache sempre que não é nulo (0 bytes não é nulo) e o regrava; a página não baixa de novo, nem depois de recarregar.
  4. content/extrator-audio.ts aceita 0 bytes; o motor recusa por "áudio ilegível" antes do ffmpeg, com duração 0,0 em 0 a 5 ms.

3. Estratégia: correção direta

Escolhida por iago às 20:02, sem debate: a causa está confirmada no código da página, sem hipóteses concorrentes.

  1. Parar de esvaziar: a ponte entrega uma cópia do buffer (bytes.slice(0)) e transfere a cópia; o buffer da página fica intacto para o cache dela.
  2. Curar a entrada vazia: se a página devolver 0 bytes, a ponte apaga só aquela entrada do cache de mídia (LruMediaStore.del(filehash)) e pede o áudio de novo, uma vez; a página baixa do servidor e grava a cópia íntegra.
  3. Nunca mandar vazio ao motor: se ainda vier vazio, ou se o módulo do cache mudou, a obtenção termina em AUDIO_INDISPONIVEL com "Não foi possível baixar o áudio do WhatsApp Web (…áudio vazio)"; o extrator confere de novo, como segunda barreira.
  4. Reparo dos dados (decisão de iago às 20:02: cura e varredura): uma varredura única no seu WhatsApp Web apaga as entradas de 0 bytes que já existem, depois que a extensão corrigida estiver carregada.

6. Riscos e o que fica de fora

change_risk: média

  • A ponte é o caminho de toda transcrição: um erro aqui para todas. Mitigado pelos testes atuais do extrator e pelos novos.
  • Dependência nova de um módulo interno do WhatsApp (WAWebMediaStore.LruMediaStore.del). Se mudar, a cura não roda e o áudio vazio vira falha legível, nunca ida ao motor.
  • A extensão passa a escrever no armazenamento da página, mas só para apagar entrada provadamente vazia, que a própria página recria.
  • A cópia dobra a memória do áudio por instantes (áudios de voz: dezenas a centenas de KB).
  • Reparo de dados (CHG-005): apaga até 31 entradas vazias; nada de valor se perde. O backup das chaves permite recriá-las, embora isso só traga o defeito de volta. Roda depois de a extensão corrigida estar carregada, senão novas transcrições voltariam a esvaziar entradas.
  • Áudio antigo, já expirado no servidor do WhatsApp: depois de apagada a entrada vazia, a página pode não conseguir baixar; aí vale o EC-02 ("Este áudio não está mais disponível no WhatsApp"), não "Falhou após 0 s".
Fora desta correção: o texto que reaparece sozinho depois de recarregar (feature à parte, RF-14); o BUG-20261002-YUB4 (▶ do WhatsApp não toca), cuja relação com este é só proposed: a varredura deve devolver ao player os áudios esvaziados, o que será conferido, mas o YUB4 relata falha também em áudios nunca obtidos pela ponte.
